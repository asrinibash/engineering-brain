# Projects

An index, not a home. One entry per thing I'm actively working on, a line or two
each, and a link to where the real work lives. Detail belongs in the project's
own repo.

## Watch the boundary here

This is the file most likely to leak company specifics, because a project *is*
a company specific. Keep entries at the level of "config-driven ingestion
pipeline for a third-party feed" rather than naming the feed, the tables, or the
system. No schemas, no table or DAG names, no hostnames, no ticket IDs, no
colleague names. If an entry would embarrass me in a screenshot, rewrite it.

Links to private repos are fine — a URL nobody can open isn't a leak. Judgment
call on employer names: I'd rather describe the work than the workplace.

## What to do with what I learn

Project-specific learning stays in the project. If something turns out to be
true beyond this one piece of work — a habit, a failure mode, a rule I want
applied next time — that's a candidate for `knowledge/`, and specifically:

- a way I want to be worked with → [../knowledge/10-collaboration.md](../knowledge/10-collaboration.md)
- a way I work through problems → [../knowledge/20-method.md](../knowledge/20-method.md)
- a tool, shell or stack fact → [../knowledge/30-environment.md](../knowledge/30-environment.md)
- craft in SQL, pandas or pipelines → [../knowledge/patterns/](../knowledge/patterns/)

Generalise it on the way in. If I can't write it without naming the employer,
it isn't ready to move.
